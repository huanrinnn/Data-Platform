qData 本地混合部署启动顺序与 DataX 注意事项

适用场景：本地源码运行 qData，依赖组件通过 Docker 或本机服务提供。

当前环境结论：前端、后端、DataX 任务均已验证可运行。

前端可启动 后端可启动 DataX 已跑通 Windows 本地环境

一、最终启动顺序

建议始终按下面顺序启动，能最大程度减少端口、依赖和配置类问题。

  1. 先启动基础依赖服务
    • MySQL
    • Redis
    • RabbitMQ
    • 如需要，再启动 DM8、DolphinScheduler 等其他依赖
    本次本地混合部署里，qdata-server 启动前必须确保 MySQL 可连，否则会报 `Communications link failure` 或 `Connection refused`。
  2. 确认 DataX 本地环境

    当前已验证通过的 DataX 目录：

    D:\qData-develop\datax

    关键结构必须存在：

    datax\bin\datax.py
datax\lib
datax\plugin
datax\job
  3. 启动后端 qdata-server 
    mvn -f D:\qData-develop\qdata-server\pom.xml -DskipTests clean package
java -jar D:\qData-develop\qdata-server\target\qdata-server.jar
    如果 `clean package` 失败并提示无法删除或重命名 `qdata-server.jar`，通常是 Windows 文件占用问题。先关闭旧进程或重启电脑后再试。
  4. 启动后端 qdata-quality 
    mvn -f D:\qData-develop\qdata-quality\pom.xml -DskipTests clean package
java -jar D:\qData-develop\qdata-quality\target\qdata-quality.jar
  5. 启动前端 qdata-ui 
    cd D:\qData-develop\qdata-ui
npm install
npm run dev
  6. 进入页面验证
    • 确认前端页面可访问
    • 确认后端接口正常
    • 确认 DataX 任务可执行

二、推荐的本地检查清单

1. Python

已验证当前环境可用：

python --version
# Python 3.11.9

2. DataX Job 目录

已验证当前目录存在：

D:\qData-develop\upload\datax\job

3. MySQL 连通性

已验证当前 DataX 业务库端口：

mysql -h 127.0.0.1 -P 3307 -u root -p

三、当前这套环境中 DataX 的最终注意事项

1. DataX 必须使用可执行发布包，不要用源码目录直接代替

错误现象：`exitCode 9009`。
原因：`datax\bin\datax.py` 不存在，或者 Python 命令不可执行。

正确做法：使用带 `bin`、`lib`、`plugin`、`job` 的官方发布包。

2. Windows 下建议固定 DataX 配置

当前已验证可用的配置思路：

datax:
  home: D:/qData-develop/datax
  python-command: python
  datax-py-path: D:/qData-develop/datax/bin/datax.py
  lib-dir: D:/qData-develop/datax/lib
  job-dir: D:/qData-develop/upload/datax/job

相比 `${user.dir}`，这种固定路径更稳，更适合 Windows 本地运行。

3. rdbmsreader / rdbmswriter 默认不一定自带 MySQL 驱动

错误现象：`No suitable driver found for jdbc:mysql://...`
原因：DataX 能启动，但对应插件的 `libs` 目录里没有 MySQL JDBC 驱动。

本次已验证需要把 MySQL 驱动放到下面两个目录：

D:\qData-develop\datax\plugin\reader\rdbmsreader\libs
D:\qData-develop\datax\plugin\writer\rdbmswriter\libs

本次使用的驱动来源：

C:\Users\ZZH20\.m2\repository\mysql\mysql-connector-java\8.0.27\mysql-connector-java-8.0.27.jar

4. 任务配置里的 writeMode 不能随意填

本次已验证：当前这套 `rdbmswriter` 不支持 `dppReplace`。

错误现象：

写入模式(writeMode)配置有误.
不支持配置参数项 writeMode: dppReplace
仅使用 insert sql 插入数据

当前环境下建议优先使用：

insert

5. 成功并不代表所有 DataX 模式都兼容

当前确认成功的是：

  • MySQL → MySQL
  • 通过 `rdbmsreader` 读取
  • 通过 `rdbmswriter` 写入
  • 写入模式使用兼容值而非 `dppReplace`

后续如果换别的数据源、别的插件、别的写入模式，仍然可能需要单独验证。

四、常见故障与快速判断

现象 大概率原因 处理建议
`DataX exitCode: 9009` 找不到 `python` 或 `datax.py` 检查 `python-command`、`datax-py-path`、DataX 目录结构
`No suitable driver found` 缺少 JDBC 驱动 把 MySQL 驱动复制到对应插件 `libs` 目录
`Communications link failure` 数据库没起来或端口不通 先确认 MySQL 实际监听端口和账号密码
`writeMode` 不支持 任务参数与当前插件版本不兼容 改为当前插件支持的写入模式，例如 `insert`
Maven 无法删除 jar Windows 文件锁 关闭旧进程、关闭占用窗口，必要时重启电脑

五、最终建议

  • 保留当前这份可运行的 `datax` 目录，不要轻易覆盖。
  • 保留已经补好的 MySQL 驱动 jar，后续迁移环境时一起复制。
  • 后续新建 DataX 任务时，先做“小表、小字段、小数据量”验证，再做正式同步。
  • 如果页面里有 `writeMode` 选项，优先选择已经验证可用的模式。
  • 每次启动顺序尽量固定：依赖服务 → 后端 → 前端 → 任务验证。
本文档根据当前 qData 本地混合部署实测过程整理，可作为后续复用的本地启动与排障参考。
